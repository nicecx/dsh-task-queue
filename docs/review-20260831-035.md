# 034 协议 v1.2：审核结论按 sessionId 路由（C 架构落地）

- requestId: 20260831-035（034 被并行会话占用，取号顺延）
- 类型: design（用户拍板 C 架构：会话自治 + 协议中心化 + 结论按 sessionId 路由）

## 背景与问题

1. **结论投递错位**（用户观察）：032/033（Insta360 会话提审）的审核结论经 Hermes RPC 投递到了主会话，而非发起会话。根因：review-handoff **request.json 不含 sessionId**（review payload 契约未定义该键），Hermes review-inbox cron 只能把 RPC 注入写死主会话。
2. **不可验证**：dsh-design-review 插件投递（startPolling→deliver）无审计日志，无法确认发起会话是否收到。
3. **版本错位**（033 changes-requested 阻塞项）：提审 docPath 快照（v0.3）与 changeFiles 实际代码（v0.4）不一致，Hermes 审到旧版——需固化纪律。

## 方案（C 架构：会话自治 + 协议中心化）

### 1. sessionId 进契约（协议 v1.2）

- review payload 契约表补 **sessionId（必填，发起会话 id）**：
  `payload: {requestId, title, docPath, changeFiles[], tests, type, urgency, sessionId}`
- 入队端补：dsh-design-review submit（design_review_submit / lesson_review_submit / auto-submit 均带 sessionId 进 payload）、review_submit.py（--session 参数或环境注入）
- 消费端透传：task_queue_consumer review handler 写 request.json 时含 sessionId（payload.sessionId → req.sessionId）
- **Hermes review-inbox cron RPC 路由**：读 request.json.sessionId → RPC 注入目标 = 该会话；sessionId 缺失 → fallback 主会话（现状）。此改动由 Hermes 侧实施（jobs.json prompt 第 6 步）

### 2. 投递审计（可验证性）

- dsh-design-review startPolling：deliver 成功/失败（含目标 sessionId）写入 design-review.log audit
- 发起会话收到结论的判定依据：审计记录 deliver ok + 会话存在

### 3. 轻量约定写入协作契约（DSH-HERMES-CONTRACT.md 新增"会话自治"节）

1. 会话命名：功能 owner 会话标题带 `[owner]` 前缀（如 `[insta360] pipeline`）——纯可读约定
2. sessionId 契约（上述 1）
3. 版本同步纪律：提审前 docPath 快照必须与 changeFiles 实际版本一致（033 教训）；docPath 快照由入队端自动生成（快照 = 提交时 README/实现的实际内容）
4. 会话自治：各会话自行闭环提审-修订-实施-验证；跨会话协助需显式请求，主会话不自动接管

### 4. 兼容与回滚

- sessionId 缺失（旧提审）→ 消费端 request.json 不写该键 → Hermes fallback 主会话（现状不变）
- 插件 deliver 审计为新增日志，不影响既有投递
- PROTOCOL.md v1.1 → v1.2（追加 sessionId 条款），文档头版本号同步
