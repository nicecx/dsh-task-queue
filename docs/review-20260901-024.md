## 023 意见逐条落实

### 1. [阻塞] reset 写路径错位（022 被吞根因）→ 已修复
**根因**：消费端 reset handler 写 `REVIEW_DIR/request.json`（review 单槽），而 reset_agent.py 从 `RESET_DIR(=~/.dsh/reset-handoff)/request.json` 读取。后果：①每次 reset 覆盖 pending review（**022 黄金仲裁正是被 f70d3c55 reset 覆盖吞掉**）②reset_agent 读到旧请求（08-31 40b541db）重放。
**修复（已落地）**：
```python
RESET_DIR = os.environ.get("RESET_HANDOFF_DIR") or os.path.expanduser("~/.dsh/reset-handoff")
# reset handler：
write_json(os.path.join(RESET_DIR, "request.json"), {...})  # 与 reset_agent.py STATE_DIR 对齐
```
- review 单槽只归 review tier 独占；reset 协议独立目录
- 测试：T11 适配（RESET_DIR mock）+ 16/16 全绿
- 遗留：reset-handoff/request.json 的旧请求（40b541db）由下次 reset 自然覆盖（写新请求）；已执行的旧请求可手工清理（实施时）

### 2. [文档更正] 积压告警 = 本方案新增（非 015 已落地）
**落实**：文档表述更正为「本方案新增：queued review ≥3 → 消费端输出稳定签名行告警（当前代码无此逻辑）」。

### 3. [建议] review 单槽覆盖可追溯 → 覆盖前 audit
**落实**（实施清单新增）：review handler 写 request.json 前，若检测到被覆盖的 pending 值（requestId 不同）→ audit 记录 `review-overwritten {oldRequestId, newRequestId}`；配合 docs/ 快照，任何被覆盖 review 可追溯恢复（孤儿检测：docs/<rid>.md 存在但无 result 且无 pending → 提示补提）。
