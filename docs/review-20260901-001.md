# 036 开发前复用检索规范（消灭"重新造轮子"）

- requestId: 20260901-001（跨天取号顺延，原 036）
- 类型: design（用户提出：每次开发新功能都要人提醒才查方案/插件/Git 借鉴——需固化为自动规范）

## 背景与问题

用户观察：**每次开发新功能，都需要用户提醒，DSH 才会去查有没有成熟方案和插件、去 Git 找借鉴；用户不介入就重新造轮子。**

现状资产盘点（实测）：
- 本地已开发插件/仓库 12+ 个（审批/队列/评审/语音/视觉/UI/日历/邮件/iMessage/看门狗…）
- awesome-dsh-plugin 收录 **2712** 个外部插件
- review-handoff docs 历史设计 35 份
- **缺口**：无"开发前必查"规范；dsh-design-review 只在写设计文档后触发（事后评审），无开发前检索环节

## 方案：四要素规范

### 1. 能力资产索引（CAPABILITY-INDEX.md，已起草 v0.1）

- 位置：~/.dsh/CAPABILITY-INDEX.md（工作区草稿已建 docs/CAPABILITY-INDEX.md）
- 内容：本地能力清单（领域分类：审批安全/协作协议/输入媒体/UI/系统工具链）+ 外部生态检索入口（awesome 2712 + GitHub）+ 历史设计入口
- 维护：随插件开发/收录更新（协作契约条款约定）

### 2. 契约新增条款"开发前复用检索"（DSH-HERMES-CONTRACT.md）

新功能/新插件开发前**必做三查**（写进设计文档"既有资产与借鉴"节）：
1. 查 CAPABILITY-INDEX（本地已有能力 → 优先复用/扩展，禁止重复造轮子）
2. 查 awesome-dsh-plugin 收录（2712 个外部插件 → 可借鉴/收录/联动）
3. GitHub 检索同类成熟方案（web_search，附链接）

三查结果必须出现在设计文档的固定章节（"复用评估"），缺该节 = 设计文档不完整（dsh-design-review 评审项之一）。

### 3. 设计文档模板"复用评估"节（dsh-design-review 强制关卡）

- 设计文档（*.design.md / 提审 doc）模板新增强制节：
  ```
  ## 复用评估
  - 本地已有能力（CAPABILITY-INDEX 条目）：xxx → 复用/扩展/新造（理由）
  - 外部收录（awesome 条目）：xxx
  - GitHub 借鉴：链接 + 结论
  ```
- **强制机制（不靠自觉）**：dsh-design-review 在提审入口（design_review_submit 工具 + auto-submit）**机器校验**：
  - 文档必须含 `## 复用评估` 节（大小写不敏感）
  - 节内必须含至少一条：CAPABILITY-INDEX 条目引用 或 awesome 条目 或 GitHub 链接（正则/关键词校验）
  - **校验失败 → 拒绝入队**（返回错误："提审被拒：缺复用评估节（开发前复用检索规范 036）"，附三查提示）——提审是互审流程的必要环节，拒绝入队 = 该设计无法进入评审 = 强制补齐
- 提审协议加结构化字段：`payload.reuseCheck = {index: [...], awesome: [...], github: [...]}`（消费端透传进 request.json，Hermes 可见可核）

### 3b. Hermes 评审双保险

- review-inbox cron 评审清单加一项：核对 request.json.reuseCheck 字段与文档复用评估节一致（缺失 → 评审备注"未做复用评估"，可在裁决中要求补充）
- 双保险：即使插件关卡被绕过（如插件未装），Hermes 裁决仍会暴露"无复用评估"

### 4. 自动化触发（后续增强，P1 后再提）

- dsh-design-review auto-submit 时：自动读取 CAPABILITY-INDEX 相关条目注入提审文档"复用评估"节（减少人工书写）
- 可选：新功能设计开始时由 agent 自动执行三查（规范内化到执行习惯，配合契约条款）
