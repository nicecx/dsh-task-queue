## 005 意见逐条落实

### 1. [必改·安全边界] 修复任务一律 tier=review，禁止 tier=fix 自动应用
**落实**：传播机制全链走互审，**不新增任何自动应用路径**：
```
lesson approved → 缺陷模式提取 → 全机扫描（grep）
  → 发起 agent 逐项复核（file + 命中行 + 上下文）→ 受影响清单
  → 每个受影响项生成 tier=review 修复任务入队（payload: 缺陷模式/文件/严重度/复核说明）
  → 消费端出队 → Hermes 逐项审核（approved/changes-requested/rejected）
  → approved 才实施修复 → 回归测试 → 完成
```
- 与契约四·六「先讨论后动手」一致：任何修复经 Hermes 裁决后才实施
- 严重度（S1/S2/S3）只影响优先级（priority 0/1/2），不影响"是否自动执行"

### 2. [必改·防误报] 命中清单须经发起 agent 逐项复核后才入队
**落实**：
- 扫描只产出**候选清单**（file + 命中行 + 上下文片段，不入队）
- lesson 发起 agent（或 lesson 钩子）逐项复核：真命中 / 假阳性（模式匹配必然产生假阳性）
- 复核后**仅真命中项**生成 review 修复任务；假阳性记录审计（action='reuse-...' 同款，action='prop-scan-fp'）
- 复核过程随 lesson 文档归档（可追溯）

### 3. [建议·落地] 已知缺陷清单落点
**落实**：
- 位置：`~/.dsh/KNOWN-ISSUES.md`（独立清单，与 OPS-GUARDRAILS 分离）
- 关系：KNOWN-ISSUES = 各插件的已知缺陷登记（模式/文件/严重度/状态：open|fixed|verified）
- OPS-GUARDRAILS 保持 append-only 守则（防复发措施），两者不混用；checkGuardrailConflict 仅用于守则追加

### 4. [建议·分工] 执行方定死
**落实**：dsh-design-review 负责（lesson approved 钩子内）：模式提取 + 扫描 + 候选清单 + 复核辅助 + 入队 review 修复任务；**Hermes 只做审核裁决**（review-inbox 既有职责）。不引入 Hermes 消费端扩展。

### 5. [建议·实现契约] core.js 模板校验扩展
**落实**（P1 实现时）：
- `checkTemplateSections(content)` 纯函数契约：返回 { ok, missing: [] }（校验 DESIGN-TEMPLATE 必填章节：复用评估/方案/接口与兼容性/安全/测试/变更文件）
